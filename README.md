     1 АНАЛИЗ ЛИТЕРАТУРНЫХ ИСТОЧНИКОВ И  
       ПРОГРАММНЫХ РЕШЕНИЙ
    
        1.1 Описание и анализ предметной области
     
     Система автоматизации записи к врачу с модулем напоминаний представляет собой специализированное программное решение, предназначенное для оптимизации взаимодействия между медицинским учреждением и пациентами. В отличие от традиционных бумажных журналов или отдельных электронных календарей, такая система изначально проектируется как целостная среда управления приёмами, объединяющая расписание врачей, механизм бронирования слотов и автоматическое информирование пациентов. Это означает, что каждая операция записи рассматривается не только как техническая фиксация времени, но и как элемент комплексного сервиса, включающего контроль занятости, обработку отмен и превентивное оповещение.
     Предметная область охватывает несколько взаимосвязанных функциональных блоков, которые в совокупности обеспечивают полный жизненный цикл записи на приём.
     Управление субъектами системы включает регистрацию пользователей (пациентов, врачей, администраторов), их идентификацию и аутентификацию, назначение ролевых полномочий, а также управление жизненным циклом учётных записей (активация, блокировка, изменение данных). На этом уровне решаются задачи создания профилей пациентов с указанием контактной информации, привязки врачей к их специализациям и кабинетам, а также разграничения доступа к функциям системы в соответствии с ролями.
     Управление расписанием обеспечивает формирование и ведение графика работы медицинских специалистов. В него входят: создание шаблонов расписания (например, «понедельник–пятница с 9:00 до 15:00»), автоматическая генерация временных слотов заданной длительности (типовой слот – 20 минут), ручная корректировка (блокировка слотов на время обеда, отпуска врача), а также отображение свободных и занятых интервалов. Каждый слот характеризуется датой, временем начала и окончания, а также флагами занят и заблокирован.
     Обработка записи на приём является ключевым с точки зрения бизнес-логики. Он реализует: поиск свободных слотов по выбранному врачу и дате, валидацию выбранного времени, создание записи со статусом PENDING (ожидает подтверждения) или CONFIRMED, автоматическое резервирование слота, а также обработку отмены или переноса записи с освобождением слота. При создании записи фиксируются дата и время визита, причина обращения, идентификаторы пациента и врача.
     Модуль напоминаний обеспечивает автоматическое уведомление пациентов о предстоящих приёмах. Для каждой созданной записи система генерирует одно или несколько напоминаний с заданными интервалами (например, за 24 часа и за 2 часа до визита). Канал связи (email, СМС) и статус отправки фиксируются в базе данных. Фоновый планировщик на сервере периодически сканирует таблицу напоминаний и, когда наступает время отправки, инициирует доставку, после чего статус меняется на SENT. Пациент может просматривать свои напоминания, изменять интервалы и каналы, а также отключать ненужные.
     Медицинская карта и отчётность агрегирует данные о завершённых и пропущенных приёмах. Врач после визита заполняет протокол: жалобы, осмотр, диагноз, назначения и рекомендации. Эта информация становится доступной пациенту в разделе «История визитов». Администратор может формировать отчёты по нагрузке врачей, явке пациентов, эффективности напоминаний и экспортировать их в формате CSV.
     Таким образом, предметная область автоматизации записи к врачу представляет собой сложную систему взаимосвязанных бизнеспроцессов и сущностей, включающую участников с различными ролями, врачебные расписания, временные слоты, записи на приём, медицинские протоколы, напоминания и аналитические отчёты. Автоматизация этой области требует специализированного программного обеспечения, сочетающего развитую логику управления расписанием, гибкую настройку напоминаний, надёжные механизмы разграничения прав доступа и мощные инструменты аналитики.
     
     1.2 Обзор функциональности аналогов программного средства
     
     Для определения оптимальных архитектурных и функциональных решений проведён сравнительный анализ трёх характерных представителей рынка систем автоматизации записи к врачу, а также одного универсального календарного сервиса, используемого в медицинской практике: специализированная медицинская информационная система «1С:Медицина», облачный сервис управления записями «YCLIENTS», комплексная платформа для клиник «MedExpert».
     «1С:Медицина» представляет собой отраслевое решение на базе технологической платформы 1С, предназначенное для автоматизации медицинских учреждений. Система обеспечивает ведение электронных медицинских карт, учёт услуг, формирование расписания врачей и интеграцию с бухгалтерским контуром предприятия. К безусловным достоинствам относятся соответствие требованиям законодательства (в том числе в части регламентированной отчётности), возможность локального развёртывания без постоянного доступа к интернету и глубокая интеграция с другими продуктами 1С. Вместе с тем модуль записи на приём в «1С:Медицина» ориентирован на работу регистратора: пациент не имеет возможности самостоятельной онлайнзаписи, а модуль напоминаний либо отсутствует, либо реализован в виде ручного обзвона. Стоимость лицензии варьируется от 200 000 до 600 000 рублей в зависимости от числа рабочих мест, дополнительно оплачивается внедрение и сопровождение. Система разворачивается на СУБД Microsoft SQL Server или PostgreSQL; для работы требуется выделенный сервер и лицензированная операционная система Windows.
     YCLIENTS является облачным сервисом для управления записью клиентов в сфере услуг. Система предоставляет пациенту возможность самостоятельной онлайнзаписи через вебинтерфейс или мобильное приложение, поддерживает автоматическую отправку SMS и emailнапоминаний, а также интеграцию с социальными сетями. Достоинствами YCLIENTS являются простота внедрения, удобный интерфейс и гибкая настройка расписания. Однако сервис является исключительно облачным, что создаёт зависимость от качества интернетсоединения и не позволяет локализовать данные на серверах медицинского учреждения (что может противоречить требованиям к защите персональных данных). Кроме того, YCLIENTS не предоставляет встроенных средств ведения электронной медицинской карты – система фокусируется исключительно на записи и учёте клиентов. Модуль напоминаний работает в режиме «fireandforget» без возможности гибкой настройки интервалов и каналов для каждого пациента. Стоимость подписки – от 1 500 до 6 000 рублей в месяц в зависимости от тарифа.
     MedExpert – комплексная система для управления частными медицинскими центрами, включающая модули расписания, электронной карты, лабораторной информационной системы и финансового учёта. Система поддерживает автоматическую рассылку напоминаний, интеграцию с сайтом клиники для онлайнзаписи и формирование аналитических отчётов. MedExpert может разворачиваться как локально, так и в облаке. К недостаткам можно отнести высокую стоимость, сложность настройки и перегруженный интерфейс. Модуль напоминаний в базовой версии отсутствует либо требует дополнительной оплаты. Пользователи отмечают недостаточную гибкость в управлении временными слотами и отсутствие функции автоматической блокировки слотов при превышении лимита записей.
     Таким образом, существует потребность в легковесном, автономном десктопном приложении, которое сочеталло бы простоту использования с ключевыми функциями: ведение картотеки врачей и пациентов, удобное расписание и, обязательно, встроенный модуль напоминаний (например, отображение списка пациентов для обзвона или автоматическая отправка email). Разработка такого приложения на платформе Java в среде IntelliJ IDEA является актуальной и позволит закрыть выявленные недостатки аналогов, предоставив медицинским учреждениям доступный и эффективный инструмент автоматизации.
     
    

   2 МОДЕЛИРОВАНИЕ ПРЕДМЕТНОЙ ОБЛАСТИ
      И РАЗРАБОТКА ТРЕБОВАНИЙ

     2.1 Анализ и формализация бизнес-процессов предметной области
     
     Business Process Model and Notation (нотация моделирования бизнес-процессов) – это система условных обозначений, которая отображает бизнес-процессы с помощью блок-схем. BPMN диаграмма показывает в какой последовательности совершаются рабочие действия и перемещаются потоки информации. 
     Четкое представление бизнес-процессов – основа успеха любого проекта и организации. Диаграммы BPMN стали универсальным языком для моделирования процессов, понятным как аналитикам, так и разработчикам. Но между созданием просто "красивой схемы" и построением действительно рабочей модели процесса лежит пропасть. Профессиональные BPMN-диаграммы позволяют не только визуализировать, но и трансформировать бизнес, обнаруживая узкие места и возможности для оптимизации.
     Эффективная система записи к врачу основывается на чётко организованных этапах, включая сбор идентификационных данных пациента, автоматическую и ручную верификацию, валидацию параметров записи, подбор свободного слота, подтверждение и отправку напоминания. При этом взаимодействие пациентов, регистраторов и врачей через приложение, а также учёт нормативных требований и политики конфиденциальности медицинских данных играют ключевую роль.
     Грамотная интеграция всех компонентов позволяет оптимизировать процесс записи, минимизировать ошибки и обеспечивать точное выполнение задач – от первичного запроса до подтверждённого визита и последующего напоминания.
     Это особенно важно для предотвращения перебоев в оказании медицинской помощи и для повышения общей эффективности операционной деятельности клиники. Продуманное управление записью к врачу способствует не только рациональному использованию рабочего времени медицинского персонала, но и долгосрочной стабильности бизнеса медицинской организации за счёт роста удовлетворённости пациентов и снижения административной нагрузки.
     
     2.2 Анализ требований к программному средству и разработка
           их спецификации
     
     Разрабатываемое приложение для автоматизации записи к врачу должно обеспечивать управление расписанием медицинских специалистов, бронирование временных слотов пациентами и автоматическую рассылку напоминаний. Бизнес-логика системы реализуется исключительно на серверной стороне. Клиентская часть обеспечивает доступ ко всем функциям через удобный графический интерфейс с разграничением прав пользователей. Система должна поддерживать не менее 15 высокоуровневых вариантов использования.
     В системе предусмотрены три роли пользователей: администратор, управляющий учётными записями и системными настройками; врач, управляющий собственным расписанием и просматривающий список пациентов; пациент, самостоятельно записывающийся к врачу и получающий напоминания.
          Такой структурированный подход позволяет выявить все возможные варианты использования системы на ранних этапах проектирования, что снижает риски появления ошибок и неучтённых требований в дальнейшем. Диаграмма вариантов использования описывает систему с точки зрения конечного пользователя, фокусируясь на том, какие цели он хочет достичь, а не на технических деталях реализации.

     2.3 Образ предлагаемого решения
     
     Разрабатываемое программное средство представляет собой десктопное клиент-серверное приложение для автоматизации записи пациентов на приём к врачам с модулем напоминаний. Система построена на основе многоуровневой архитектуры, в которой серверная часть реализует основную бизнес-логику, проверку прав доступа, взаимодействие с базой данных и фоновую отправку уведомлений, а клиентская часть предоставляет графический интерфейс пользователя, реализованный на платформе JavaFX. Такое разделение обеспечивает независимую разработку и модификацию каждого уровня, а также централизованное хранение и защиту данных.
     Взаимодействие между клиентом и сервером осуществляется по сети с использованием TCP/IP-сокетов. В качестве прикладного протокола обмена данными применяется передача сериализованных объектов команд (класс Command). Каждый запрос клиента представляет собой экземпляр Command, содержащий тип операции (перечисление CommandType), параметры в виде ассоциативного массива строк и токен сессии для аутентификации запросов (поле sessionToken), отсутствующее только у публичных команд LOGIN, REGISTER и PING. Ответ сервера также формируется в виде объекта Command, в котором поле статуса (CommandStatus) принимает значения OK, CLIENT_ERROR или SERVER_ERROR, а дополнительная информация возвращается в параметрах и поле message. Передача данных реализована посредством сериализации Java-объектов.
     Серверное приложение функционирует как долгоживущий процесс, прослушивающий входящие TCP-соединения на заранее сконфигурированном порту 5555. Каждое новое подключение передаётся на обработку отдельному потоку (ClientThread), что позволяет параллельно обслуживать запросы нескольких клиентов без взаимных блокировок. Для взаимодействия с базой данных используется выделенный синглтон-объект DBhelper, обеспечивающий пул соединений с PostgreSQL и централизованное выполнение SQL-запросов. Безопасность пользовательских паролей гарантируется хранением их SHA-256-хешей и использованием уникальных токенов сессий, срок действия которых ограничен.
     Представленная функциональная архитектура демонстрирует модульный подход к построению системы с радиальной топологией информационных потоков. Центральным связующим звеном выступает ядро – «Система управления записью на приём с модулем напоминаний». Оно выполняет роль диспетчера, маршрутизируя запросы от клиентов к соответствующим обработчикам, обеспечивая многоуровневую валидацию операций и поддерживая целостность бизнес-логики.
     Вокруг ядра сгруппированы специализированные функциональные модули, осуществляющие обмен данными с центром:
     Аутентификация и контроль доступа. Модуль отвечает за первичную безопасность системы. Он передаёт в ядро введённые пользователем логин и пароль. После успешной верификации ядро создаёт сессию и возвращает клиенту токен, идентификатор пользователя и его роль (PATIENT, DOCTOR, ADMIN). Все последующие запросы снабжаются этим токеном, что позволяет серверу однозначно идентифицировать пользователя и проверять его права.
     Управление пользователями и ролями. Инструмент администрирования персоналом. Модуль направляет в систему команды на получение списка всех пользователей, блокировку/разблокировку учётных записей, удаление пользователей и изменение их ролей. В ответ сервер предоставляет актуальный список пользователей с указанием ролей, статусов и дат создания. Предусмотрена защита от блокировки или удаления самого себя и других администраторов.
     Управление справочником врачей. Модуль предоставляет интерфейс для добавления, редактирования и деактивации врачей. Данные о специализациях, номерах кабинетов, образовании и стаже врачей передаются в ядро, которое синхронизирует их с базой данных. Клиентские приложения пациентов и администратора получают актуальный перечень врачей для записи на приём.
     Запись на приём. Рабочий модуль пациента и администратора. Входящий поток данных содержит выбранного врача, дату, временной слот и причину обращения. Ядро системы проверяет доступность слота, создаёт запись со статусом PENDING, бронирует выбранный слот и автоматически генерирует два напоминания о предстоящем приёме (за 24 часа и за 2 часа). Клиенту возвращается подтверждение с идентификатором созданной записи.
     Управление расписанием врачей. Модуль отображает недельную сетку слотов с цветовой индикацией занятости. Врач может блокировать отдельные слоты, что исключает их из доступных для записи. Ядро системы при каждом запросе возвращает актуальное состояние слотов, учитывая как бронирования пациентов, так и ручные блокировки.
     Медицинская карта и история визитов. Модуль обеспечивает ведение электронной медицинской карты. Врач заполняет протокол приёма (жалобы, осмотр, диагноз по МКБ-10, назначения), который передаётся в ядро и сохраняется в связанной таблице visit_details. Запись переводится в статус COMPLETED, слот освобождается, а напоминания отменяются. Пациент видит хронологию завершённых визитов и неявок с указанием диагнозов и назначений.
     Напоминания. Интеллектуальный компонент системы. При создании записи ядро автоматически формирует напоминания с заданными интервалами. Фоновый планировщик на сервере периодически сканирует таблицу напоминаний и для тех, чьё время отправки наступило, выполняет отправку уведомления и помечает их как отправленные (SENT). Пациент может просматривать свои напоминания, изменять интервал, канал или отключать их.
     Аналитика и отчётность. Модуль визуализации бизнес-показателей. Администратор выбирает тип отчёта, период и детализацию. Ядро системы на основе агрегированных данных из базы формирует CSV-файл с UTF-8 BOM для корректного отображения кириллицы, который сохраняется на компьютере администратора.
     Системные журналы. Модуль аудита всех критических действий. Каждая операция (вход, запись, отмена, сохранение диагноза) регистрируется ядром в таблице audit_log с указанием пользователя, типа действия, затронутой сущности и уровня важности (INFO, WARN, ERROR). Администратор имеет возможность просматривать журнал с фильтрацией по пользователю, действию и уровню, а также выполнять поиск по содержимому.
     Хранение и защита данных. Физический уровень архитектуры, реализованный на реляционной базе данных PostgreSQL. Ядро системы отправляет SQL-запросы через слой DAO. База данных выполняет запросы, обеспечивает ссылочную целостность и каскадное удаление связанных записей, а также возвращает извлечённые наборы данных для дальнейшей обработки серверной логикой.
     Определены особенности функционирования бизнес-процессов после внедрения разрабатываемого программного средства. В результате автоматизации будет создана единая информационная среда, обеспечивающая сквозной процесс записи пациента к врачу – от выбора специалиста и бронирования времени до сохранения медицинского протокола и получения назначений. Автоматическая генерация напоминаний и их фоновая отправка снижают частоту неявок и повышают дисциплину лечения. Многоуровневая система ролей и токенов гарантирует, что каждый пользователь видит только свою информацию, а административные действия протоколируются для последующего аудита. Тесная интеграция всех модулей позволяет исключить ручное управление расписанием, минимизировать ошибки при записи и существенно повысить эффективность работы регистратуры и врачей. Внедрение спроектированной архитектуры обеспечит высокую отказоустойчивость системы, надёжную защиту персональных данных и позволит руководству медицинского учреждения принимать эффективные управленческие решения на основе оперативной и достоверной аналитики.
     По результатам второй главы можно сформулировать следующие выводы. Разработанные UML-диаграммы обеспечивают полное формальное описание бизнес-процессов системы: от аутентификации пользователей и записи на приём до формирования отчётов и отправки напоминаний. Спроектированная реляционная база данных из одиннадцати нормализованных таблиц с внешними ключами и ограничениями целостности гарантирует корректное хранение и связность данных. Сформулированные функциональные требования охватывают полный жизненный цикл приёма, а нефункциональные требования закрепляют критерии безопасности, производительности и переносимости. Предложенный образ решения в виде клиент-серверной архитектуры на TCP/IP-сокетах с протоколом сериализованных команд и радиальной топологией десяти специализированных модулей создаёт исчерпывающую основу для проектирования и разработки программного средства[8].

          3 ПРОЕКТИРОВАНИЕ И РАЗРАБОТКА 
        ПРОГРАММНОГО СРЕДСТВА
     
      3.1 Архитектурные решения и технологии реализации 
            программного средства
     
     В процессе проектирования архитектуры разрабатываемого программного средства для автоматизации записи к врачу ключевым этапом являлся выбор модели реализации и взаимодействия компонентов системы. Были рассмотрены три основных архитектурных подхода: монолитное приложение, веб-ориентированная система и классическое клиент-серверное приложение.     
      Анализ показал, что клиент-серверная архитектура на базе TCP/IP является оптимальной для системы контроля корпоративных расходов, так как обеспечивает максимальную скорость валидации транзакций в реальном времени, централизованную безопасность и независимость от качества внешнего интернет-соединения.
      Для реализации серверной части был выбран язык программирования Java 21 LTS. Выбор обусловлен статусом долгосрочной поддержки, мощной экосистемой, строгой типизацией, встроенной поддержкой многопоточности и современными языковыми конструкциями, которые значительно повышают надёжность и читаемость кода медицинской системы[11].
           В результате анализа было выбрано полноценное десктопное приложение на JavaFX. Такое решение обусловлено следующими преимуществами: удобство работы с графическим интрефейсом намного выше, чем с консольным, для коммерческого использования внешний вид приложения играет значимую роль, поэтому консольный интерфейс не подходит.
     
     В качестве СУБД выбрана PostgreSQL. Данная система демонстрирует отличные показатели как реляционная СУБД с открытым исходным кодом, полностью соответствующая требованиям ACID. PostgreSQL оптимизирована для широкого спектра операций, поддерживает горизонтальное масштабирование, предлагает надёжные механизмы безопасности, включая ролевую модель доступа и шифрование данных.
     Разработка программного обеспечения ведётся под операционной системой Windows, что обусловлено её доминирующим положением на рынке. Данная платформа обеспечивает бесшовную интеграцию с IntelliJ IDEA и нативную поддержку Java без необходимости дополнительной конфигурации.
     В качестве основной среды разработки применяется IntelliJ IDEA – функциональный инструмент с продвинутыми возможностями автодополнения кода, инструментами рефакторинга и комплексными средствами отладки[15]. Важным преимуществом является полная совместимость с JavaFX и встроенная поддержка системы сборки Maven, что оптимизирует управление зависимостями.
     Диаграмма развёртывания (Deployment Diagram) в нотации UML показывает физическое распределение компонентов системы. Клиентский узел содержит Java-приложение с GUI на JavaFX. Серверный узел содержит Java ServerSocket-приложение с бизнес-логикой и модулем напоминаний, а также СУБД PostgreSQL. Взаимодействие клиента и сервера осуществляется через TCP/IP-сокеты в локальной сети. Сервер взаимодействует с почтовым SMTP-сервером для отправки напоминаний пациентам.
     
     Диаграмма компонентов системы включает следующие ключевые модули. На стороне клиента: графический интерфейс на JavaFX, включающий формы входа, записи к врачу, просмотра расписания; клиентский сокет, обеспечивающий сетевое соединение с сервером. На стороне сервера: серверный сокет, принимающий входящие подключения; обработчики запросов по типам: LoginHandler, AppointmentHandler, ReminderHandler, AdminHandler; слой бизнес-логики с сервисами: AppointmentService, ReminderService, UserService; DAO-слой (Data Access Objects) для работы с БД; база данных PostgreSQL.
     
     Пользовательский интерфейс представляет собой совокупность программных и аппаратных средств, обеспечивающих взаимодействие пользователя и вычислительной системы. На начальном этапе разработки пользовательского интерфейса осуществляется распределение функций приложения по экранам, определяются макеты экранов и их содержимое; определяются элементы управления и их поведение.
     На начальном этапе разработки программного средства были разработаны прототипы пользовательского интерфейса, чтобы определить графическое оформление будущего приложения.
     При входе в систему (авторизации) перед пользователем будет отображаться окно входа. 
     
     Главное окно пациента будет содержать таблицу с историей назначений от врачей, плашку с кнопкой для записи к врачу и ссылки для перехода на остальные страницы приложения. 
    
     На странице каталога врачей будет представлен список всех доступных для записи врачей, поле для удобного поиска специалиста по имени или специальности а также фильтры для специализации и времени.
     
          
     Записи пациента к врачам будут в отдельном окне, которое будет содержать действующие записи, поле для их поиска, фильтры, а так же плашки с количеством предстоящих, завершённых, отменённых записей и неявок.
     
     Эти прототипы представляют собой начальную визуализацию интерфейса приложения. На текущем этапе они выполняют несколько важных функций в процессе проектирования: во-первых, помогает структурировать основные разделы приложения, включая главную страницу с логотипом, навигационное меню и раздел истории посещений; во-вторых, позволяет предварительно оценить логику взаимодействия пользователя с системой. 
     Такой макет, несмотря на свою простоту, уже позволяет проанализировать несколько аспектов будущего приложения: удобство навигации, достаточность предоставляемой информации в разделе заказов и пользователей, необходимость дополнительных функциональных элементов. 
     Дальнейшее развитие этих прототипов должно включать несколько направлений работы: добавление дополнительных интерактивных элементов управления (кнопки, фильтры, формы), расширение системы навигации (дополнительные меню, ссылки), введение визуальных акцентов для улучшения восприятия информации, проработку состояний интерфейса для различных сценариев использования, а также другие страницы для реализации поставленных задач.
          
     Схема базы данных представляет собой фундаментальный каркас, который определяет архитектуру хранения информации. Она включает в себя совокупность таблиц, их атрибутов, взаимосвязей между ними, а также накладываемых ограничений и спецификаций типов данных. Этот концептуальный макет выполняет роль технического руководства, регламентирующего принципы хранения и обработки данных в системе.
     Физическая схема, изображенная на рисунке 3.7, представляет фактическую структуру физического хранилища базы данных на диске. Он включает в себя механизмы хранения, файловые структуры, индексы и другие детали низкого уровня, которые определяют, как данные хранятся и получают к ним доступ со стороны базовой системы управления базами данных (СУБД). Этот тип схемы в основном связан с эффективным использованием пространства хранения, повышением производительности базы данных за счет оптимизации операций поиска и хранения данных.
     
     Логический уровень, представленный на рисунке 3.10, выступает промежуточным звеном между физической реализацией и концептуальным представлением. Он описывает данные в терминах таблиц, полей, связей и ограничений, формируя четкую структуру, понятную разработчикам приложений. На этом уровне определяются первичные и внешние ключи, типы данных, триггеры и хранимые процедуры. Логическая схема не зависит от способа физического хранения, что позволяет изменять параметры производительности без переделки структуры таблиц.
     
     Концептуальный уровень представляет собой наиболее абстрактное представление данных, ориентированное на бизнес-пользователей. Он фокусируется на сущностях предметной области, их атрибутах и взаимосвязях, игнорируя технические детали реализации. Этот уровень служит общим языком общения между заказчиками, аналитиками и разработчиками, помогая корректно отразить бизнес-процессы в структуре базы данных. Здесь важны не технические параметры, а смысловая нагрузка данных и их роль в бизнес-логике. Такая модель изображена на рисунке 3.9.

     Представленные схемы базы данных предназначены для приложения записи к врачу. Оно позволяет эффективно управлять расписанием врачей, пользователями системы и процессом обработки записи. Рассмотрим каждую таблицу и их взаимосвязи более подробно.
     Таблица пользователей (users). Центральной таблицей системы является таблица пользователей, хранящая учётные данные всех участников – пациентов, врачей и администраторов. Каждый пользователь имеет уникальный числовой идентификатор (id). Поле login содержит электронную почту, которая используется как уникальное имя для входа в систему. В целях безопасности пароль хранится в виде хэш-суммы (password_hash), что исключает возможность чтения исходного пароля даже при компрометации базы данных. Дополнительное поле salt усиливает защиту паролей. Роль пользователя (role) определяет его права и доступный интерфейс: пациент записывается на приёмы и просматривает свою историю, врач работает с расписанием и заполняет протоколы, администратор управляет справочниками и аудитом. Флаг blocked позволяет временно или навсегда заблокировать учётную запись без её удаления, сохраняя все связанные данные. Дата создания (created_at) фиксирует момент регистрации.
     Таблица сессий (sessions). Для поддержания безопасного доступа после входа пользователя в систему создаются сессии. Каждая сессия привязана к конкретному пользователю (user_id) и содержит уникальный токен (token), который передаётся клиентом при каждом запросе к серверу вместо повторной отправки пароля. Сессия имеет ограниченный срок жизни (expires_at), после которого токен становится недействительным. IP-адрес (ip_adress) сохраняется для дополнительного аудита безопасности. Таблица связана с users каскадным удалением – при удалении пользователя все его сессии автоматически уничтожаются.
     Таблица специализаций (specializations). Справочник специализаций является простой таблицей-словарём, содержащей идентификатор и название специализации (например, «Терапевт», «Стоматолог»). Она служит для нормализации данных врачей и позволяет легко расширять перечень медицинских направлений без изменения структуры других таблиц.
     Таблица врачей (doctor). Профиль врача расширяет учётную запись пользователя медицинской информацией. Связь с таблицей users осуществляется через внешний ключ user_id, что позволяет врачу входить в систему со своими персональными данными. Поле full_name хранит полное имя врача, отображаемое в каталоге и интерфейсе пациента. Специализация (specialization_id) связывает врача с конкретным направлением. Номер кабинета (office_number) и данные об образовании (education) дают пациенту дополнительную информацию. Поле about может содержать свободное описание квалификации. Стаж (experience_years) и стоимость приёма (price) используются при сортировке и фильтрации врачей в каталоге. Флаг active позволяет отключать врача из доступных для записи, не удаляя его исторические данные.
     Таблица пациентов (patients). Аналогично врачам, профиль пациента дополняет запись в users персональными медицинскими данными. Связь user_id является обязательной и уникальной для каждого пациента. Помимо полного имени (full_name) хранятся контактные данные (phone, email), дата рождения для определения возраста, номер полиса ОМС (policy), информация об аллергиях (allergy) и группа крови (blood_type). Эти сведения отображаются в электронной медицинской карте (ЭМК) при приёме врача. Каскадное удаление гарантирует целостность: при удалении пользователя-пациента удаляется и его профиль.
     Таблица временных слотов (schedule_slots). Расписание врачей представлено слотами – минимальными временными интервалами, доступными для записи. Каждый слот относится к конкретному врачу (doctor_id) и содержит дату (slot_date), время начала (start_time) и окончания (end_time). Флаг booked показывает, занят ли слот в данный момент; при отмене или завершении приёма слот автоматически освобождается. Флаг blocked используется врачом или администратором для временного блокирования времени (например, на учёбу или совещание). Уникальность слота гарантируется составным ключом по врачу, дате и времени начала, что исключает дублирование.
     Таблица записей на приём (appointments). Эта таблица объединяет пациента, врача и выбранный слот в одну запись о приёме. Связи с patients (через patient_id) и doctors (через doctor_id) являются обязательными. Связь со слотом (slot_id) опциональна – слот освобождается при отмене записи, но история сохраняется. Дата и время приёма (appointment_datetime) фиксируются как единое значение, независимо от слота. Статус (status) проходит жизненный цикл: PENDING (ожидает подтверждения), CONFIRMED (подтверждено), COMPLETED (приём завершён), либо CANCELLED (отменено) или MISSED (неявка). Причина обращения (reason) вводится пациентом при записи. Дата создания (created_at) используется для аналитики.
     Таблица деталей визита (visit_details). При завершении приёма врач заполняет медицинский протокол, который сохраняется в таблице visit_details. Она связана один-к-одному с записью (appointment_id). В протокол входят жалобы пациента (complaints), результаты объективного осмотра (examination), код диагноза по МКБ-10 (diagnosis_code) и его текстовое описание (diagnosis_text), выписанные назначения (prescription)и дополнительные заметки врача (notes). Эти данные немедленно становятся доступны пациенту в его медицинской карте и истории визитов, а также отражаются в истории назначений на главной панели пациента.
     Таблица напоминаний (reminders). Для каждого созданного приёма автоматически генерируются напоминания, которые хранятся в этой таблице. Каждое напоминание ссылается на конкретный приём (appointment_id). Время отправки (scheduled_send_time) рассчитывается как разница между временем приёма и интервалом (interval_minutes), например, за 1440 (24 часа) или 120 минут. Канал связи (channel) определяет способ отправки (Email, Push, SMS). Статус (SCHEDULED, SENT, CANCELLED) отслеживает жизненный цикл уведомления. Флаг enabled позволяет отключить конкретное напоминание без удаления. При отмене приёма все запланированные напоминания автоматически переходят в статус CANCELLED.
     Таблица журнала аудита (audit_log). Все критические действия в системе регистрируются в таблице аудита. Для каждого события сохраняется идентификатор пользователя (user_id), его логин, тип действия (action), тип затронутой сущности (entity_type), её идентификатор (entity_id), человекочитаемое описание (details), уровень важности (level: INFO, WARN, ERROR) и временная метка (timestamp). Связь с users не является жёстким внешним ключом, что позволяет сохранять записи даже после удаления пользователей. Эта таблица используется администратором для мониторинга и расследования инцидентов.
     Таблица настроек уведомлений (notification_settings). Каждый пользователь может настроить глобальные параметры получения напоминаний. Таблица связана один-к-одному с users через user_id. Флаги channel_email, channel_push, channel_sms активируют соответствующие каналы. Интервалы interval_24h, interval_2h, interval_30min определяют, за какое время до приёма отправлять уведомления. Чтобы не беспокоить пользователя в ночное время, можно включить «тихие часы» (quiet_hours_enabled)и задать их границы (quiet_from, quiet_to).
     Центральными связующими таблицами являются users, doctors, patients и appointments. Пользователь после регистрации получает роль; в зависимости от роли создаётся связанная запись либо в doctors, либо в patients. Это позволяет врачу и пациенту использовать один механизм аутентификации (через sessions), но видеть разные интерфейсы и данные.
     Запись на приём (appointments) связывает пациента и врача через временной слот (schedule_slots). При успешной записи слот помечается занятым (booked=true), и создаются напоминания в таблице reminders. После завершения приёма врач заполняет visit_details, статус записи становится COMPLETED, слот освобождается, а напоминания переходят в CANCELLED. Вся эта информация немедленно отражается в интерфейсах: пациент видит назначения в «Истории назначений» и в «Медицинской карте», врач – завершённый приём в своей истории.
     Архитектура системы построена по классической клиент-серверной модели. Клиентское приложение (JavaFX) отправляет команды (Command) на сервер, который через слой DAO взаимодействует с базой данных. Сессии поддерживаются токенами, что исключает необходимость постоянной передачи пароля. Ролевой доступ (PATIENT, DOCTOR, ADMIN) ограничивает видимые функции: пациент не может редактировать расписание врача, а врач не может записываться на приём. Все модификации критических данных (создание/отмена записи, сохранение диагноза) протоколируются в AUDIT_LOG, обеспечивая прослеживаемость действий.
     Такая нормализованная структура базы данных гарантирует целостность информации, исключает дублирование и позволяет масштабировать функциональность системы независимо в разных компонентах – будь то добавление новых специализаций, каналов напоминаний или расширение медицинского протокола.
     Центральное место в архитектуре занимают классы, связанные с обработкой пользователей системы. Класс User описывает общую модель пользователя и содержит данные авторизации, роли и состояния учётной записи. С ним связаны классы, отвечающие за хранение сессий пользователей и настройку уведомлений. В системе предусмотрены различные роли пользователей: пациент, врач и администратор.
     Класс Doctor реализует модель врача и содержит сведения о специализации, стаже работы, стоимости приёма, кабинете и дополнительной информации. Класс связан с сущностью специализации (Spezialisation) и используется при формировании расписания и создании записей на приём. Для хранения информации о пациентах используется класc Patient, содержащий персональные данные, контактную информацию и медицинские сведения.
     Для организации расписания врачей используется клаcc ScheduleSlot, описывающий временные интервалы приёма. Каждый слот связан с конкретным врачом и содержит информацию о дате, времени начала и окончания, а также о доступности слота для записи.
     Процесс записи пациента к врачу реализуется посредством класса Appointment. Данный класс связывает пациента, врача и выбранный временной слот. В объекте записи хранится дата и время приёма, причина обращения и текущий статус записи. Для хранения результатов приёма и медицинских данных используется класс VisitDetails, содержащий жалобы пациента, результаты осмотра, диагноз, назначения и комментарии врача.
     Модуль напоминаний реализован с помощью класса Reminder. Он хранит информацию о времени отправки уведомления, используемом канале связи (Email, SMS или Push-уведомление), статусе отправки и параметрах активности напоминания. Дополнительно реализован класс NotificationSettings, позволяющий пользователю настраивать каналы уведомлений, интервалы отправки и режим тихих часов.
     Для регистрации действий пользователей и отслеживания событий системы используется класс AuditLog. В журнале аудита сохраняются сведения о выполненных операциях, типе сущности, уровне события и времени его возникновения.
          
     На диаграмме также представлены сервисные и инфраструктурные классы серверной части приложения. Они обеспечивают обработку клиентских запросов, выполнение бизнес-логики, взаимодействие с базой данных PostgreSQL и обмен данными между клиентом и сервером. Между классами реализованы отношения ассоциации, зависимости, наследования и композиции, что отражает взаимодействие компонентов системы и распределение ответственности между ними.
     
     Начальным состоянием процесса является нахождение пользователя в каталоге врачей. После выбора врача открывается диалог записи на приём. В данном состоянии отображается мини-карточка выбранного врача, календарь для выбора даты приёма, поле для ввода причины обращения и кнопка «Записаться», которая изначально неактивна.
     После выбора даты в календаре приложение переходит в состояние загрузки свободных временных слотов. На этом этапе клиентское приложение отправляет серверу запрос GET_SLOTS, содержащий идентификатор врача и выбранную дату. Во время ожидания ответа комбобокс выбора времени переводится в состояние загрузки и отображает соответствующее сообщение.
     После получения ответа от сервера система переходит в состояние отображения загруженных слотов. Если на выбранную дату существуют свободные интервалы времени, комбобокс становится активным, а первый доступный слот выбирается автоматически. Если свободных слотов нет, комбобокс блокируется, а пользователю отображается сообщение о недоступности записи на выбранную дату.
     Далее пользователь выбирает удобное время приёма и вводит причину обращения. После нажатия кнопки «Записаться» приложение переходит в состояние отправки запроса на сервер. На данном этапе формируется команда BOOK_APPOINTMENT, содержащая идентификатор врача, выбранного слота, дату и время приёма, а также текст причины обращения. Во время отправки кнопка записи становится неактивной для предотвращения повторной отправки запроса.
     После отправки данных система переходит в состояние ожидания ответа сервера. По завершении обработки сервер возвращает результат выполнения операции, после чего приложение переходит в состояние обработки ответа.
     Если сервер возвращает успешный результат (OK), система переходит в состояние успешного создания записи. Пользователю отображается уведомление об успешной записи на приём, диалоговое окно закрывается, а список «Мои записи» автоматически обновляется.
     Если сервер возвращает ошибку (CLIENT_ERROR или SERVER_ERROR), приложение переходит в состояние отображения ошибки. В данном состоянии пользователю выводится сообщение с описанием проблемы, после чего интерфейс возвращается к диалогу записи, а кнопка «Записаться» вновь становится активной, позволяя повторить попытку записи.
     На рисунке 3.11 представлена диаграмма последовательности для процесса записи пациента к врачу в клиент-серверной системе.
     Пациент начинает с выбора врача через интерфейс «Каталог врачей», после чего переходит к диалогу записи, где выбирает дату и ожидает загрузки свободных временных слотов. Система отправляет на сервер запрос с параметрами врача и выбранной даты; сервер, получив запрос, обращается к базе данных для получения списка незанятых и незаблокированных слотов. Получив подтверждение о наличии свободного времени, сервер возвращает клиенту список доступных интервалов, и клиент отображает их в виде выпадающего списка. Пользователь выбирает подходящее время, указывает причину обращения и подтверждает запись. Клиентское приложение отправляет запрос на бронирование, содержащий идентификаторы пациента, врача, слота, а также причину и дату. Сервер проверяет корректность переданных данных и наличие профиля пациента, после чего создаёт запись в базе данных со статусом «Ожидает», одновременно помечая выбранный слот как занятый и регистрируя событие в журнале аудита. На следующем этапе сервер генерирует два автоматических напоминания о предстоящем приёме (за 24 часа и за 2 часа), сохраняя их в соответствующей таблице. Завершив обработку, сервер возвращает клиенту успешный ответ, а клиент уведомляет пользователя об успешной записи и обновляет интерфейс раздела «Мои записи». В дальнейшем фоновый планировщик периодически проверяет наличие запланированных напоминаний с наступившим временем отправки и имитирует их доставку, фиксируя статус «Отправлено».

     При запуске приложения пользователь попадает на экран входа, где ему предлагается два варианта действий: авторизоваться под существующей учётной записью или создать новую. При выборе регистрации открывается форма с полями для ввода полного имени, адреса электронной почты, пароля и его подтверждения. Клиентская часть выполняет валидацию введённых данных: проверяется заполнение всех полей, корректность формата email, длина пароля не менее восьми символов, а также совпадение пароля и его подтверждения. Если валидация не пройдена, соответствующие поля подсвечиваются, и пользователь остаётся на форме до исправления ошибок. При успешной валидации клиент вычисляет хеш пароля по алгоритму SHA-256 и отправляет на сервер команду REGISTER, содержащую полное имя, email и хеш[9]. Сервер проверяет, не занят ли указанный email, и при отрицательном результате создаёт новую запись в таблице пользователей с ролью PATIENT, а также связанную с ней запись в таблице пациентов. После успешного создания учётной записи сервер возвращает клиенту токен сессии, идентификатор пользователя и роль. Клиент, получив ответ, уведомляет пользователя об успешной регистрации и автоматически выполняет вход, открывая главное окно пациента. Если же сервер сообщает о том, что email уже используется, клиент отображает ошибку рядом с полем email и возвращает пользователя к редактированию.
     При выборе авторизации открывается форма с полями email и пароля. Клиент проверяет заполнение полей и длину пароля, после чего отправляет команду LOGIN, передавая email и хеш пароля. Сервер ищет пользователя с указанным email и сравнивает хеш; если учётная запись не найдена, пароль не совпадает или учётная запись заблокирована, сервер возвращает ошибку авторизации. Клиент, получив такой ответ, отображает сообщение «Неверный email или пароль» и даёт возможность повторить ввод. В случае успешной аутентификации сервер создаёт новую сессию, сохраняет её в базе данных и возвращает клиенту токен, идентификатор пользователя, роль и полное имя. Клиент, проанализировав значение роли, выполняет перенаправление: для роли PATIENT загружается главная страница пациента с персональным приветствием, для DOCTOR – рабочее окно врача с его реальной специализацией, а для ADMIN – интерфейс администратора с панелью управления.
     
     Процесс начинается с перехода авторизованного пациента в раздел «Каталог врачей». Клиент отправляет запрос GET_ALL_DOCTORS, получает от сервера список активных врачей и отображает их в виде карточек. Пациент выбирает нужного врача и нажимает кнопку «Записаться», после чего открывается диалог записи с календарём, полем причины обращения и неактивной кнопкой подтверждения.
     Далее пациент выбирает дату в календаре (доступны только дни начиная с завтрашнего). Клиент отправляет серверу команду GET_SLOTS с идентификатором врача и выбранной датой. Сервер обращается к базе данных и получает список слотов, у которых флаги BOOKED и BLOCKED установлены в FALSE. На этом этапе процесс разветвляется:
     Если свободные слоты отсутствуют, клиент отображает сообщение «Нет свободных слотов», комбобокс времени остаётся заблокированным, и пациент возвращается к выбору другой даты.
     Если слоты найдены, клиент заполняет выпадающий список доступными временными интервалами и активирует кнопку «Записаться». Пациент выбирает подходящее время, вводит причину обращения и подтверждает запись.
     При нажатии кнопки «Записаться» клиент формирует команду BOOK_APPOINTMENT, передавая идентификаторы врача, слота, пациента, а также дату, время и причину. Сервер выполняет следующие операции: создаёт запись в таблице appointments со статусом PENDING, помечает выбранный слот как занятый (booked = true), генерирует два напоминания: за 24 часа и за 2 часа до приёма регистрирует событие в журнале аудита.
     После успешного выполнения всех операций сервер возвращает клиенту ответ со статусом OK. Клиент отображает уведомление «Запись успешно создана», закрывает диалог записи и обновляет раздел «Мои записи», где новый приём появляется во вкладке «Предстоящие». Процесс завершается.
     Таким образом, диаграмма деятельности наглядно демонстрирует последовательность действий, условия ветвления и взаимодействие компонентов системы, обеспечивающих корректную запись пациента на приём.
     
     Диаграмма деятельности описывает алгоритм генерации аналитических отчётов администратором. Процесс начинается с перехода администратора в раздел «Отчёты», где отображаются четыре карточки типов отчётов: «Нагрузка по врачам», «Статистика явки», «Эффективность напоминаний» и «Активность пациентов». Администратор выбирает нужный тип отчёта и нажимает кнопку «Сформировать», после чего открывается диалоговое окно с параметрами. В диалоге пользователь указывает период отчёта, формат (CSV) и детализацию (по дням, неделям или месяцам). При нажатии кнопки «Сформировать» выполняется проверка корректности дат: если даты не указаны или конечная дата предшествует начальной, отображается предупреждение, и пользователь возвращается к редактированию параметров. Если даты указаны верно, система открывает стандартный диалог сохранения файла, позволяя выбрать место и имя файла.
     После выбора места сохранения начинается генерация файла. Создаётся CSV-файл с кодировкой UTF-8 и обязательной записью метки порядка байтов для корректного отображения кириллицы в Microsoft Excel. В файл последовательно записываются: заголовок отчёта с его названием, период и детализация, а затем данные, соответствующие выбранному типу. Для отчёта «Нагрузка по врачам» подсчитывается количество приёмов для каждого врача; для «Статистики явки» – количество неявок в разрезе специализаций; для «Эффективности напоминаний» – общее количество, количество отправленных и запланированных уведомлений; для «Активности пациентов» – частота обращений каждого пациента. Источником данных служат уже загруженные в память списки записей и напоминаний, полученные администратором при входе в систему.
     После формирования содержимого файл сохраняется на диск. Если сохранение прошло успешно, администратору отображается уведомление с указанием полного пути к сохранённому файлу. В случае ошибки записи на диск выводится сообщение об ошибке. Процесс завершается закрытием диалога и возвратом к списку отчётов. Таким образом, диаграмма демонстрирует последовательность действий пользователя, логику проверки входных данных и взаимодействие с файловой системой, обеспечивающее получение отчётов в машиночитаемом формате.
          
     Разработанная система управления складскими запасами реализует комплексный подход к информационной безопасности, соответствующий современным стандартам защиты данных. В основе системы лежит многоуровневая архитектура безопасности, включающая несколько взаимодополняющих механизмов защиты.
     Ключевым элементом системы является строгая процедура аутентификации и авторизации с разделением пользователей на три категории: пациенты, врачи и администраторы. Каждой категории назначены четко определенные права доступа, что исключает возможность несанкционированного выполнения операций. Процесс регистрации включает обязательную верификацию контактных данных для предотвращения создания фальшивых аккаунтов.
     Для защиты передаваемых данных используется протокол TCP, обеспечивающий надежную доставку и целостность информации. Дополнительно реализованы механизмы контроля последовательности пакетов и проверки их подлинности. Критически важные операции, такие как авторизация, защищены современными алгоритмами шифрования.
     Хранение учетных данных организовано с применением криптографических методов. Пароли пользователей хранятся в хешированном виде с использованием уникальной «соли» для каждой учетной записи, что делает невозможным восстановление исходных паролей даже при компрометации базы данных.
     Система включает надежную защиту от SQL-инъекций через использование параметризованных запросов к базе данных. Дополнительно реализована многоуровневая валидация и фильтрация входных данных на уровне приложения.
     Таким образом, система обеспечивает комплексную защиту данных на всех уровнях впв – от аутентификации пользователей до хранения информации, что позволяет эффективно противостоять современным угрозам информационной безопасности.

Реализованное приложение позволяет существенно повысить эффективность управления потоками пациентов, свести к минимуму ошибки при записи на приём и оптимизировать все ключевые административные процессы медицинского учреждения. Встроенная система напоминаний о предстоящих визитах способствует снижению частоты неявок пациентов и повышению дисциплины лечения, а персонализированные рабочие места врача и администратора ускоряют обработку медицинской документации и формирование отчётности.

Внедрение подобных решений позволяет медицинским организациям не только оптимизировать текущие бизнес-процессы, но и получить значительное конкурентное преимущество на динамично развивающемся рынке медицинских услуг.

Листинг скрипта инициализации базы данных
     
DO $$
BEGIN
    IF NOT EXISTS (SELECT 1 FROM pg_type WHERE typname = 'role') THEN
        CREATE TYPE role AS ENUM ('PATIENT', 'DOCTOR', 'ADMIN');
    END IF;
END$$;

CREATE TABLE IF NOT EXISTS users (
    id BIGSERIAL PRIMARY KEY,
    login VARCHAR(255) NOT NULL UNIQUE,
    password_hash VARCHAR(255) NOT NULL,
    salt VARCHAR(255),
    role role NOT NULL DEFAULT 'PATIENT',
    blocked BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE IF NOT EXISTS sessions (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    token VARCHAR(255) NOT NULL UNIQUE,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    expires_at TIMESTAMP NOT NULL,
    ip_address VARCHAR(45)
);

CREATE TABLE IF NOT EXISTS specializations (
    id SERIAL PRIMARY KEY,
    name VARCHAR(255) NOT NULL UNIQUE
);

CREATE TABLE IF NOT EXISTS doctors (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT REFERENCES users(id) ON DELETE SET NULL,
    full_name VARCHAR(150) NOT NULL,
    specialization_id INT REFERENCES specializations(id),
    office_number VARCHAR(10),
    education TEXT,
    about TEXT,
    experience_years INT DEFAULT 0,
    active BOOLEAN NOT NULL DEFAULT TRUE,
    price INT NOT NULL DEFAULT 0
);

CREATE TABLE IF NOT EXISTS patients (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    full_name VARCHAR(255) NOT NULL,
    phone VARCHAR(50),
    email VARCHAR(255),
    date_of_birth DATE,
    policy VARCHAR(100),
    allergy VARCHAR(500),
    blood_type VARCHAR(10)
);

CREATE TABLE IF NOT EXISTS schedule_slots (
    id BIGSERIAL PRIMARY KEY,
    doctor_id BIGINT NOT NULL REFERENCES doctors(id) ON DELETE CASCADE,
    slot_date DATE NOT NULL,
    start_time TIME NOT NULL,
    end_time TIME NOT NULL,
    booked BOOLEAN NOT NULL DEFAULT FALSE,
    blocked BOOLEAN NOT NULL DEFAULT FALSE
);

CREATE TABLE IF NOT EXISTS appointments (
    id BIGSERIAL PRIMARY KEY,
    patient_id BIGINT NOT NULL REFERENCES patients(id) ON DELETE CASCADE,
    doctor_id BIGINT NOT NULL REFERENCES doctors(id) ON DELETE CASCADE,
    slot_id BIGINT REFERENCES schedule_slots(id) ON DELETE SET NULL,
    appointment_datetime TIMESTAMP NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    reason TEXT,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE IF NOT EXISTS visit_details (
    id BIGSERIAL PRIMARY KEY,
    appointment_id BIGINT NOT NULL UNIQUE REFERENCES appointments(id) ON DELETE CASCADE,
    complaints TEXT,
    examination TEXT,
    diagnosis_code VARCHAR(50),
    diagnosis_text VARCHAR(500),
    prescription TEXT,
    notes TEXT,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE IF NOT EXISTS reminders (
    id BIGSERIAL PRIMARY KEY,
    appointment_id BIGINT NOT NULL REFERENCES appointments(id) ON DELETE CASCADE,
    scheduled_send_time TIMESTAMP NOT NULL,
    interval_minutes INT NOT NULL,
    channel VARCHAR(20) NOT NULL DEFAULT 'EMAIL',
    status VARCHAR(20) NOT NULL DEFAULT 'SCHEDULED',
    enabled BOOLEAN NOT NULL DEFAULT TRUE,
    actual_send_time TIMESTAMP
);

CREATE TABLE IF NOT EXISTS audit_log (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT,
    user_login VARCHAR(255),
    action VARCHAR(100),
    entity_type VARCHAR(100),
    entity_id VARCHAR(100),
    details TEXT,
    level VARCHAR(20),
    timestamp TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
